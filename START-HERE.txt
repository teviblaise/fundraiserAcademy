FUNDRAISER ACADEMY — LAPTOP PREVIEW

1. Install the current Node.js 24 LTS release from https://nodejs.org.
2. Extract the ZIP, then open a terminal in the fundraiserAcademy folder.
3. Run: npm ci
4. Run: npm start
5. Open http://localhost:3000 in your browser.

Keep the terminal open while using the website. Press Ctrl+C to stop it.
On Windows, these commands work in PowerShell or the VS Code terminal.
Use npm start rather than the VS Code Live Server extension: this website
includes a Node.js backend for registration, trading, and certificates.

Registration opens the client dashboard with your saved details. New accounts
must confirm their email before starting the assessment. Configure Resend with a
verified sender and a public HTTPS origin for this same server; local HTTP previews
can show public pages and pending client profiles, but cannot deliver a working
confirmation or password-recovery link without that setup. Existing accounts keep their prior access.
Crypto demo fills use fresh
Coinbase reference prices; intraday forex fills need a configured Twelve Data key.
Ten forex pairs are available, including yen and sterling crosses. Their profit,
margin, and risk are valued in USD using fresh conversion references.
Trade sizes are entered in lots: 1 forex lot is 100,000 base units; 1 crypto lot
is 1 coin. Crypto reference prices use a live stream when available. Forex Basic
uses periodic provider quotes. The dashboard labels the active price feed.
Missing or stale quotes pause trading. Earlier demo accounts can start a new
reference-priced attempt using Reset demo, with previous records preserved. Cloud-instance users
and secrets are excluded from this export. Your laptop creates its own
private data folder. Required signup confirmations and optional email alerts need
Resend sender configuration; background push also needs HTTPS/browser permission;
in-page popup notifications work without provider credentials.

See README.md for features and DEPLOYMENT.md for later live hosting.

After passing the assessment, open Trader agreement. Signing is compulsory
before sponsorship review. The agreement stays pending until the company
provides its contract. No contract terms are included in this preview.

Support is available from the floating Support button. Basic company answers use
an Academy guide without credentials. Generative AI needs SUPPORT_AI_API_KEY;
human replies need a registered, verified staff account in SUPPORT_STAFF_EMAILS.
Conversation requests are saved and queued; an agent is not automatically online.
See README.md for staff access and DEPLOYMENT.md for the hosted configuration.

The Contract trader leaderboard at /leaderboard.html shows consenting current
contract signers by verified qualifying-assessment return. It does not show live
sponsored-account results. Sign in on that page to choose a public alias and
visibility. The board stays empty until eligible traders opt in.

Forgot your password? Use Forgot password on the login page. The latest email
link works once and expires in 20 minutes. A reset signs out all devices and
keeps your assessment history. Delivery uses the same verified Resend sender
and public HTTPS origin as signup confirmation; no links appear in the API.

Open Security from the client dashboard to set up an authenticator app and manage
signed-in devices. Confirm your email before enrolling an authenticator; the
Security page offers a confirmation email button. Save the ten one-time recovery
codes before leaving the page.
Password recovery keeps two-factor authentication enabled. Use a fresh app code
for each security change or a different unused recovery code.

Your private data folder includes two-factor-key.json and a separately generated
backup-key.json unless stable encryption keys are directly configured. Keep both
private and preserve the required keys for their existing records/artifacts.
The backup encryption key needs a separate secure copy; it is deliberately not
inside the backup it decrypts. This download never includes another installation's keys.

STAFF AND ADMINISTRATION

The admin dashboard is /admin.html. It includes trader and assessment review,
certificates, agreement publication, sponsorship decisions, sponsored-account
and payout records, MetaTrader connections, performance analysis, account-closure
requests, backup/error operations, support, reports, staff roles, audit history,
and system status.

Set ADMIN_OWNER_EMAILS in the application server's environment to the exact
registered owner email. Register normally, confirm that email using the configured
verified Resend sender, then enable an authenticator in Security. Admin access
requires all these steps; setting the email alone never bypasses them. On Render,
add the variable to that service's Environment settings separately and redeploy.
A setting saved in the Codex cloud environment does not update Render.

Sensitive changes and report exports require your password and a fresh second
factor in the console. The confirmation lasts five minutes for the current session.
Owners manage roles for registered, verified, 2FA-enabled staff. Trusted server
operators can use npm run admin:staff -- list, grant, or revoke; see README.md for
the full commands. These operations cannot bypass email confirmation or 2FA.

Financial entries record verified external activity. Staff must enter the actual
agreement's profit split and sharing policy. The website does not purchase prop
accounts or send money. Your client dashboard shows your own review message and
recorded accounts and payouts; internal notes remain private to authorized staff.
Back up the database and private keys together on persistent storage. The free
Render preview cannot preserve lasting account, agreement, or financial records.


ACCOUNT CONTROLS AND PAYOUTS

Open /account-tools.html from the client dashboard or Security. You can download
your complete paginated personal-data export, request account closure, and request
a payout from your unreserved recorded earned share. Each action needs a separate
password confirmation and a fresh second factor when enabled. Confirmation lasts
five minutes for that session and action. Keep the same payout request key when
retrying an uncertain request; the website handles this to avoid duplicate holds.
Payout approval and recorded payment history do not send a bank transfer.

Account closure requires typing DELETE MY ACCOUNT. Staff roles, open sponsored
allocations, pending payouts, or unsettled earned shares keep it pending so you can
resolve them; a pending request can be cancelled. Completed closure signs out all
devices, removes mutable operational personal data, and returns a retention
receipt. Immutable agreements, financial records, review/audit history, and older
backup copies may remain as disclosed. This does not claim that every personal
datum has been erased. Save the receipt and apply the company's retention policy.

METATRADER CONNECTIONS AND PERFORMANCE

MetaTrader 4/5 synchronization uses MetaApi. Set METAAPI_API_TOKEN privately on
the actual application server; on Render this is separate from Codex settings.
Create/deploy the permitted connection in MetaApi, then link its existing account
ID to the approved academy sponsored record in the admin console. Never enter a
broker password or API key into that form or chat. The website reads performance;
it does not provision accounts, trade, purchase accounts, or transfer money.

Choose the history start deliberately (default: the previous 30 days). The server
checks active links roughly every 60 seconds while running. Missing credentials,
stale observations, and partial history are shown rather than replaced with demo
results. Broker currency remains native, and deposits are not trading profit.
Staff must reconcile actual settlements before posting profit statements or
payout earnings to the separate financial ledger.

Open /performance.html for observed equity, realized balance, monthly results,
drawdown, and consistency. Marked equity starts when actual observations exist;
the site does not invent older equity. Read history/currency/fee coverage notes.
MetaTrader closing fills may include partial closes, so their win rate is not a
round-trip-position win rate. Consistency statistics add no new challenge rules.

OPERATIONAL HEALTH, BACKUPS AND RECOVERY CHECKS

Open Admin > Operations & recovery to check current database/storage health,
backup freshness, delivery failures, email/forex setup, stale active MetaApi feeds,
and safe runtime/storage metrics. Refresh the view or download its sanitized
aggregate report. The report excludes customer records, provider account IDs,
filesystem paths, and secret values.

Run diagnostics requires your current staff authentication and an audit reason.
It runs SQLite quick_check/foreign-key checks in a bounded read-only subprocess and tests
private storage using a temporary file that is removed. Recorded results do not
repair records, send email, contact providers, or replace the live database.
Configured email still needs a real inbox test; free disk space does not prove
persistent or offsite storage. See the operational runbook in DEPLOYMENT.md for
flagged checks and never put passwords or API keys into a reason or chat.

The running server schedules encrypted local SQLite backups, initially after about
30 seconds, then by default every 24 hours with seven artifacts retained by count.
Operations & recovery shows sanitized errors, job history, and isolated recovery
checks. Defaults can be changed with BACKUP_DIRECTORY, BACKUP_INTERVAL_HOURS,
and BACKUP_RETENTION_COUNT. Preserve the separate backup encryption key.

Local backups are not offsite backups. Use persistent private storage and a
separate operator-managed offsite process before relying on real records. Losing
an ephemeral Render instance can lose its database, backup files, and keys together.

Trusted operators can run npm run operations -- status, backup, or verify.
Use npm run operations -- health for aggregate readiness, or npm run operations
-- diagnose for recorded local database/storage diagnostics. Health exits 0 for
healthy and 2 for attention/critical. Diagnostics exits 0 for ok and 2 for
warning/critical. Command failures exit 1. The CLI does not start background
schedulers; inspect the running server's workers from Admin.
The restore command writes only to a NEW directory and requires the healthy
current database and latest deletion ledger. It never replaces the running
database and is not complete recovery after losing the database or host. Restored
accounts require password resets; old sessions, tokens, and recovery codes are
revoked, while authenticator protection stays enabled with its original key.
See DEPLOYMENT.md for exact commands, requirements, and recovery limitations.
